# 段階 5 の障害時の挙動と長時間の利用の確認

## はじめに

段階 5 では、文字起こしの接続が切れたときの自動の再接続、ping による切断の検知、指定した時間での自動停止を実装しました。この報告は、依頼者が 2026-11-10 に OBS で行ったネットワークの切断の確認と、65 分以上の連続の確認の結果をまとめたものです。計画は Beads の課題 `obs-realtime-translate-summary-rbg.5` の design にあります。

## 検証方法

- 切断の確認: 動作中に依頼者が PC のネットワークを 30 秒ほど切ってから戻し、続けて 3 分以上切った。手順書は `.prompts/MANUALS/2026-11-10-stage5-network-check.md`
- 長時間の確認: 自動停止を 70 分に設定して開始し、開始から約 59 分に依頼者が発話した。手順書は `.prompts/MANUALS/2026-11-10-stage5-long-run.md`
- 判定には OBS のログのうちプラグインが書いた行を使った。抜粋は `docs/logs/2026-11-10-stage5-reconnect-obs-log-excerpt.txt`

## 検証結果

### 切断の確認

OBS のログ 2026-11-10 21-07-47.txt で確かめた事実は次のとおりです。

| 時刻 | 事象 |
| --- | --- |
| 21:09:35 | 音声の送信の失敗 (Failed sending data to the peer) で切断を検知 |
| 21:09:37 | 1 回目の再接続 (待機 0.99 秒) で接続。待機の間にたまった音声 225,351 フレームを破棄 |
| 21:09:42、21:09:46 | 英訳が成功。再接続のあとも英訳が古い連番として捨てられていない |
| 21:09:57 | ping を送り、0.135 秒後に PONG を受信 |
| 21:10:16 | 長い切断の開始。音声の送信の失敗で検知 |
| 21:10:18 から 21:10:36 | 名前解決の失敗で 2 回目から 5 回目の再接続を使い切り、停止 |

依頼者は、短い切断のあとに操作なしで字幕と英訳が再び出たこと、長い切断のあとに停止して原因が表示されたことを確かめました。

### 長時間の確認

OBS のログ 2026-11-10 22-19-39.txt で確かめた事実は次のとおりです。

| 時刻 | 事象 |
| --- | --- |
| 22:28:34 | 開始 |
| 23:27:29 から 23:27:44 | 依頼者の発話で英訳と概要が成功 |
| 23:27:54 | 概要の要求が 1 回失敗 (Timeout was reached、11,397.8 ms) |
| 23:28:34.881 | 接続から 3,600.0 秒で error (error_type=invalid_request_error、error_code=session_expired) を受信し、同時に終了コード 1001 で閉じられた |
| 23:28:36.646 | 待機 0.73 秒の 1 回目の再接続で接続 |
| 23:38:34 | 開始から 70 分で自動停止 |

再接続のあとの接続は 598.0 秒続き、PONG を 29 回受信しました。英訳は 11 件すべて成功し、概要は 7 件成功、1 件失敗でした。依頼者は再接続のあとに発話していません。

検証の途中で、依頼者が開始/停止の切り替えのホットキーにスペースキーを割り当てていたため、22:20 から 22:27 にほかのアプリでの入力のたびに開始と停止が約 25 回切り替わりました。ホットキーを外して 22:28:34 に開始し直しています。

## 考察

文字起こしのセッションにも 60 分の上限があり、上限では session_expired の error のあとに接続が閉じられると考えています。error のあと 5 秒以内に閉じた接続を再試行の対象にする扱いにより、上限に達しても 2 秒以内に復帰できると考えています。

再接続のあとに字幕が再び出ることは、長時間の確認では観測していません。同じ再接続の経路を通る切断の確認で英訳の再開を観測しているため、依頼者と合意のうえ、65 分以上の連続利用で字幕が止まったままにならないという完了の条件は満たしたと判断しました。

上限の前に計画的に接続し直す仕組みは作らないと判断しました。上限での切断で失われるのは、切断の瞬間に未確定だった発話だけと考えているためです。

ping による切断の検知は、今回の 2 回の切断ではどちらも使われず、音声の送信の失敗で先に検知しました。ping は送信の失敗が起きない種類の切断に備えるものだと考えています。

## 確認の過程で直したこと

- 依頼者の指摘で、英訳と概要の失敗の警告が開始からの累計で出続けていたのを、直近の要求が失敗している間だけ出す形に直した。文言も「概要の生成に失敗しました。画面には最後に成功した概要を残しています」のように、失敗した側が分かる形にした
- 切り替えのホットキーをほかのアプリでの入力で押すキーに割り当てると意図せず切り替わるため、README のホットキーの説明に注意を加える案を依頼者に示している
